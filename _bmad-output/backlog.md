## Ideas

### Tools component: script-backed MCP tools + macOS TCC permissions carrier
User writes a script (any language) that optionally accepts parameters and returns output, then declares it in config to expose it as an MCP tool callable by agents. The bus wraps the script, handles invocation, and returns output. Config controls which agents can call which tools (per-tool agent allowlist). Secondary role: act as a long-lived process that holds macOS TCC grants (Calendar, Contacts, Reminders, etc.) so agents can invoke sensitive system operations through it without each needing their own TCC authorization. Needs a spike covering: config schema for tool declarations, parameter passing/output capture, per-agent allowlisting, and TCC entitlement strategy.

### Interrupt in-flight turn on rapid follow-up message; retry with both combined
Today `HeadlessInstance.enqueue()` (`src/adapters/cc-headless.ts:176`) serializes messages per contact via a Promise chain keyed in `this.queues` (a `Map<string, Promise<void>>`, line 162): if message B arrives while message A's `claude -p` turn (spawned in `invokeClaude()`, line 213) is still running, B simply waits its turn — it doesn't start until A's entire turn (tool calls + reply delivery) finishes. Chris wants different behavior: if a subsequent message arrives *before* the current turn's reply has actually been delivered, abort the in-flight turn and retry with a single new turn containing both messages combined as input, rather than processing them as two sequential, context-blind turns.

Real use case this fixes: sending a message, then immediately sending a clarification or correction before the first reply lands (e.g. the "I meant Apple Card stuff" correction pattern already seen in production) currently produces two disjointed replies instead of one turn with full context up front.

Needs a spike covering:
- **Interrupt trigger**: define "reply hasn't been delivered yet" precisely — not just "the `claude -p` child hasn't exited," but "no `reply()`/`send_message()` tool call has completed for this turn." A fixed debounce window is the cheap alternative but would add latency to every single-message turn, not just rapid-fire ones.
- **Abort mechanic**: killing the in-flight child (`child.kill()`) is straightforward, but needs to happen cleanly mid-stream (partial stdout parsing, no corrupted `--resume` session state for the retry). **Update (2026-08-18)**: researched whether the CLI has a lighter-weight "steer" primitive (Chris's typo-correction scenario — separate ask, same underlying mechanism). Findings: (1) today's `invokeClaude()` (cc-headless.ts:265) passes the prompt as a CLI arg and never opens stdin, so there's no live channel into a running turn at all — a prerequisite fix regardless of approach. (2) Switching to `--input-format stream-json` (alongside the `--output-format stream-json` we already use) opens a persistent stdin channel, but per the CLI's own control protocol and a live upstream issue (anthropics/claude-code #41665), there is no non-interrupting steer primitive — a plain user message sent mid-turn over stdin just queues silently until the current turn naturally finishes. To actually cut in requires sending an explicit `{"type":"control_request","request":{"subtype":"interrupt"}}` first, which halts at the next safe point (discarding the in-flight step) and returns a receipt (including `still_queued` — what messages are still pending) — then the new/corrected message goes in. **Conclusion: this is the same feature as the interrupt-and-combine idea above, not a separate lightweight mechanism — no need to design two things.** Recommend implementing the abort mechanic via this documented `interrupt` control request rather than a raw `child.kill()` — it's a clean protocol-level soft-stop with a receipt, instead of a SIGKILL that risks corrupting the stdout stream-json parse mid-message.
- **Side-effect risk**: if the interrupted turn already executed a side-effecting tool call (sent a reminder, wrote a Capital OS transaction, sent an email) before being killed, that isn't undone — worth deciding whether to allow interruption at all once irreversible tool calls have started, or only before the first tool call.
- **Combining messages**: how the retry prompt merges the original message with the follow-up — simple concatenation vs. a structured "message, then a follow-up arrived" framing so the agent doesn't just see them as unrelated instructions.
- **Scope**: per-contact (matching the existing `queues` key) or per-session/topic, given the separate Threaded Mode / DM-topics backlog item above would introduce topic-scoped sessions.

**Note (2026-08-18, Chris)**: a real new wrinkle surfaced while building/testing E29 (live tool-call status stream) — Peggy's turns don't actually end when `reply()`/`send_message()` fires; she keeps working afterward doing her own post-reply memory logging (reading/editing daily files, MEMORY.md, project files). Under the interrupt-and-combine design above, a legitimate next message arriving during that post-reply window would abort an in-flight turn that has *already delivered its real answer* and is just doing housekeeping — not the "still drafting the actual response" case this idea was designed around. Killing that mid-flight risks corrupting/half-writing memory files, and combining the new message with an already-answered turn doesn't make sense the way it does for a genuine pre-reply interruption.

Chris's suggested direction: **don't have interruption logic reach into post-reply memory work at all** — instead, move memory-logging out of the main conversational session entirely, into a separate agent or process that runs after (or independent of) the turn that produces the user-facing reply. That would cleanly separate "the thing that can legitimately be interrupted" (in-progress drafting, pre-reply) from "the thing that should never be interrupted by a new message" (post-reply bookkeeping) — worth folding into the spike's scope alongside the interrupt-trigger/abort-mechanic/side-effect-risk questions already listed above.

**Added benefit, same note**: today's per-contact serialization (`HeadlessInstance.enqueue()`, `this.queues`) doesn't let message B start until message A's *entire* turn finishes — including A's post-reply memory bookkeeping, even though A's actual answer already went out. Offloading memory-logging to a separate agent/process fixes responsiveness too: the main session frees up (and the queue can advance to the next message) as soon as the reply fires, instead of making the next message wait through housekeeping it has no reason to be blocked on.

**Open design question, same note (2026-08-18)**: once memory-logging moves to a separate agent/process, when should it actually fire? Firing it after every single reply is wasteful — most turns have nothing new worth logging. Recommend an idle-debounce: reset a timer on each inbound message, fire the sweep after ~3-5 min of conversation silence, plus a hard ceiling (~20-30 min) so a long uninterrupted back-and-forth still flushes periodically rather than deferring indefinitely. Checked `cc-headless.ts` — sessions already resume via `--resume`, so the full transcript persists independently of when memory files get written; a delayed sweep risks brief staleness, not data loss (`search_transcripts` can always recover the raw material), which makes debouncing low-risk here. Exception: high-stakes items (financial decisions, health/scheduling commitments) should still trigger an immediate out-of-band write rather than waiting on the debounce.

**→ Promoted to E30 (backlog 2026-08-18).** The whole memory-decoupling thread above (post-reply risk, responsiveness fix, debounce/ceiling firing model, high-stakes exception) is now fully specced as its own epic: `_bmad-output/epics/E30-decoupled-memory-logging.md`. This backlog item's remaining scope narrows to the interrupt/steering mechanism itself — E30 is a prerequisite for it, not a duplicate.

### Tool-call status stream (E29): escape/backtick underscored values before sending to Telegram
Confirmed 2026-08-20: `src/adapters/tool-call-summary.ts`'s `formatToolCallSummary()` interpolates raw dynamic values — `file_path` (Read/Edit/Write), Bash/Agent `description`, Grep `pattern`, WebFetch `url`, WebSearch `query`, and the tool `name` itself in the generic fallback — directly into the status line with no escaping. `src/adapters/telegram.ts:516` sends/edits these lines with `parse_mode: 'Markdown'`, where a bare `_` is an emphasis delimiter. Any interpolated value containing an underscore (a snake_case file path, a tool name like `search_transcripts`, a Python module, etc.) risks Telegram either mis-rendering it as italics or outright rejecting the message as malformed Markdown — the latter is already visible in production logs as recurring `Markdown parse error for editMessageText/sendMessage, retrying plain text` lines (`telegram.ts:521`), which currently masks the problem by silently dropping to plain text (losing all formatting) rather than fixing the source. Fix: wrap each interpolated dynamic field in backticks (renders as inline code, exempt from further Markdown parsing) in `tool-call-summary.ts` before it's embedded in a status line — cheaper and more correct than escaping every Markdown special character by hand, and matches how the values are conceptually code/paths anyway.

### cc-headless / sub-agent auth: per-agent env file configuration
Today every `claude -p` spawn (cc-headless.ts:213) inherits the bus-core process's full `process.env` as-is — auth rides on whatever ambient OAuth/keychain session the operator's machine has, with no per-agent isolation. Dig into supporting a per-agent env file (e.g. `env_file: .env.peggy` on a `cc-headless` instance, or per-agent in the `agents:` block) so an agent can authenticate with its own `ANTHROPIC_API_KEY` or other env vars, separate from AgentBus's own environment or the Claude Code CLI's default OAuth/keychain auth. Relevant context: `--bare` mode (considered and dropped for the sub-agent-spawning epic) requires `ANTHROPIC_API_KEY`/`apiKeyHelper` since it skips OAuth/keychain reads entirely — this backlog item is about giving *any* headless agent or spawned sub-agent that same kind of explicit, isolated auth without forcing `--bare`.

### Email: strip token-heavy noise from forwarded/inbound bodies
Forwarded emails (especially HTML newsletters and receipts) carry a lot of content that costs tokens but adds no signal once converted to text: very long tracking/click-through URLs, `data:` URIs (inline base64 images/fonts), unsubscribe/preference footers, repeated whitespace, and link soup. The inbound path (`resolveInboundText` / `htmlToPlainText` in `src/adapters/email-render.ts`, plus `selectInboundBody`) currently passes the converted text through largely intact. Add a configurable cleanup pass that: truncates or drops long query-string tracking URLs (keep the host/path, strip `?utm_*`/long opaque tokens), removes `data:` URLs entirely, collapses excessive blank lines, and optionally trims known boilerplate footers (unsubscribe blocks). Keep it conservative (never drop the user's note or core forwarded content) and measure token savings on a few real forwards. Consider a per-adapter `inbound_cleanup` config toggle and a max-body-size guard.

### get_transcript MCP tool: fetch full session transcript by ID
Agent can already search transcripts (FTS5) and list/get sessions, but cannot retrieve the full ordered message history for a specific session. Add a `get_transcript` MCP tool backed by a new `GET /api/v1/sessions/:id/transcript` endpoint that returns all transcript rows for a session in chronological order. Enables the agent to pull full conversation context when a memory reference or `list_sessions` result points to a relevant prior session.

### Slash command cleanup: retire replay + legacy DB-memory commands
The built-in command set still carries surfaces tied to subsystems that E20 left dormant or that no longer earn their place. Prune them and tighten the registry:
- **Replay family** — `/replay`, `/next`, `/cancel` (paginated transcript playback in `src/commands/handlers.ts`, plus `playbackStates` and `paginateLines`). Rarely used; the transcript/`get_transcript` path is the better tool.
- **Legacy memory commands** — `/forget` (expires `memories` rows) and `/retry_summary` (re-queues summarization). Both target the E8/E9 structured-memory store, which E20 turned off by default (`memory.structured_extraction: false`) in favor of the agent's own files. With the DB store dormant these are vestigial for headless agents.

Scope: remove the handlers + their registrations in `createBuiltinCommands`, drop the now-dead helpers/state, prune the tests, and update `docs/SLASH_COMMANDS.md`. Decide whether to keep `/forget` behind a capability check for any remaining MCP-store deployments or delete outright. Net effect: the autocomplete menu and `/help` shrink to the commands that still matter (`/status`, `/pause`, `/resume`, `/sessions`, `/schedule`, `/clear`, `/help`).
